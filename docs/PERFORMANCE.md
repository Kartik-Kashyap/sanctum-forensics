# SANCTUM — Performance Evaluation

> **Status of the figures in this document.**
>
> Every number in a SANCTUM performance report is produced by running
> `python -m tools.benchmark` on the machine being described. The figures in §7
> were produced by exactly that command, and the raw output is checked in under
> `bench_final/PERFORMANCE.md` alongside the machine-readable
> `bench_final/benchmark.json`. Nothing here is estimated.
>
> Read §7 with §5 in hand: the environment block comes first, and the
> verification ratios are the portable figures.

---

## 1. What is measured, and why each one

| Measurement | The question it answers |
|---|---|
| **Erase throughput** | Is whole-device sanitization practical on this machine? |
| **Verification cost** | What does read-back verification add to the wall clock? |
| **Carve throughput** | How long does scanning a given image take? |
| **Recovery accuracy** | Are the recovered bytes *correct*? |
| **Peak allocation** | Does scanning memory scale with image size? |
| **File-erase rate** | How many files per second can be securely deleted? |

Accuracy is listed separately from throughput on purpose. Throughput is
worthless if the bytes are wrong, and a benchmark that reports only MB/s is
measuring the disk, not the tool.

---

## 2. Method

### 2.1 Throughput is attributed, not claimed

Erase throughput is dominated by the storage device. SANCTUM writes a fixed
pattern in 1 MiB chunks and the drive decides how fast that happens. The report
therefore prints the machine, the processor and the storage under test
alongside every figure, so a reader can judge whether the numbers transfer to
their own hardware.

`tracemalloc` is used for the memory measurement because it reports
*Python-level* allocation. That is the right instrument for the claim being
tested — that the carver works in fixed-size blocks and does not hold the image
in memory — because OS-level RSS would be dominated by page cache and would
hide the property under test.

### 2.2 Accuracy is measured against ground truth

The carved-file corpus is generated by `tools/fat16.py`, which builds a FAT16
filesystem image from scratch and records, for each planted file, its cluster
chain and its SHA-256 digest in `manifest.json`.

Recall and precision are then computed as:

```
recall    = |recovered digests ∩ deleted-file digests| / |deleted-file digests|
precision = |recovered digests ∩ all planted digests| / |recovered digests|
```

Both sides of the comparison are digests. A carver that returns garbage scores
zero on precision. A carver that returns nothing scores zero on recall. Neither
can be gamed by finding *something*.

### 2.3 Each figure is a median of repeats

Erase and verification figures are medians over `--repeats` runs (default 3),
not single samples. Storage performance is noisy — background writeback, other
processes, and thermal state all move the number — and a median is a more
honest summary than a mean that a single stall can drag.

### 2.4 Quick mode is labelled as such

`--quick` uses small images and one repeat. It exists to check the harness
works, not to produce a report. It prints `QUICK MODE: these figures are
indicative only, not a measurement.` and sets `"quick_mode": true` in the JSON,
so a quick run cannot be mistaken for a real one after the fact.

## 3. What the harness cannot measure

1. **Real device performance.** Every erase measurement is against a file on a
   filesystem, which the OS caches. A byte written to a file in the page cache
   is not the same cost as a byte written to a spinning platter or a NAND
   page. The figures are an *upper bound* on device throughput, and the report
   says so.

2. **Firmware sanitize commands.** ATA SANITIZE, NVMe Format/Sanitize and TCG
   Opal crypto erase are issued by the drive's controller and their timing is a
   property of the device. SANCTUM does not issue them; it recommends them and
   warns when an overwrite is the wrong instrument.

3. **Real-world recovery accuracy.** The corpus is synthetic FAT16 with a known
   planted set. It establishes that the engine is correct on known ground
   truth. It does not predict a recall rate for a real NTFS volume that has
   been in use for five years, and no benchmark of this shape could.

4. **The cost of forensic completeness.** The measurements are of the engines
   under the settings used. Turning on fragment reassembly, or scanning for all
   37 signatures rather than a narrow filter, changes the numbers, and the
   report does not model that.

grows roughly in proportion to the image, the carver is buffering the source
and the claim is false.

## 5. Reading a SANCTUM performance report

**Compare like with like.** A throughput figure measured on a file in the page
cache is not comparable to one measured on bare metal. Read the *Environment*
block first.

**Look at verification overhead as a ratio, not a time.** `overhead_vs_unverified`
is the number that decides whether FULL verification is affordable on a 2 TB
drive, and it is far more portable between machines than the absolute seconds.

**Treat recall and precision as the headline.** They are the only figures in
the report measured against cryptographic ground truth.

**Be sceptical of a single sample.** If `repeats` is 1, the run was a smoke
test.

## 6. Reproducing the measurement

```bash
# Full measurement: writes bench/benchmark.json and bench/PERFORMANCE.md
python -m tools.benchmark

# The run behind the figures in §7
python -m tools.benchmark --output bench_final

# Smoke run: small sizes, one repeat, clearly labelled as indicative
python -m tools.benchmark --quick

# Choose the output directory and repeat count
python -m tools.benchmark --output results/ --repeats 5
```

The harness needs no arguments and no configuration. It creates its scratch
images under `<output>/work/`, uses a separate audit chain per benchmark, and
does not touch the application's own data directory. The verification section
takes at least seven samples whatever `--repeats` says, for the reason given in
§7.2.

Reproducing §7 exactly means running the second command and comparing the
environment block before anything else; §5 says why.

Two useful one-off commands, which measure the same engines under the same
conditions as the correctness tests:

```bash
# Recovery accuracy, with the corpus manifest printed
python -m pytest tests/test_carver.py -q -s

# The whole system, headless, with a PASS/FAIL summary
python run.py --selftest
```

## 7. Figures from the reference run

Produced by `python -m tools.benchmark --output bench_final` on the development
machine for this build. The verbatim harness output is checked in at
`bench_final/PERFORMANCE.md`; `bench_final/benchmark.json` holds the same data
machine-readably. The environment block is reproduced first because §5 says any

```

Processor:         AMD64 Family 25 Model 80 Stepping 0, AuthenticAMD
Storage under test: C:\  (SATA/NVMe SSD, page cache warm)
Native backend:    ACTIVE — SleuthKit filesystem parsing (NTFS/FAT/ext);
                   EnCase E01 image support (pytsk3, pyewf installed)
```

Earlier revisions of this document were produced with the native backend absent,
and their figures were the pure-Python path. Those figures are superseded by the
run below and are no longer reproduced; the portable path itself remains in the
code and is what the tool falls back to wherever `pytsk3` or `pyewf` cannot be

### 7.1 Erase throughput

| subject | passes | median_s | MB/s | bytes written | repeats |
|---|---|---|---|---|---|
| zero1 @ 16 MB | 1 | 0.042 | 516.1 | 16,777,216 | 3 |
| dod3 @ 16 MB | 3 | 0.087 | 615.4 | 50,331,648 | 3 |
| dod7 @ 16 MB | 7 | 0.192 | 595.7 | 117,440,512 | 3 |
| gutmann @ 16 MB | 35 | 0.863 | 663.5 | 587,202,560 | 3 |
| zero1 @ 64 MB | 1 | 0.111 | 680.9 | 67,108,864 | 3 |
| dod3 @ 64 MB | 3 | 0.293 | 646.5 | 201,326,592 | 3 |
| dod7 @ 64 MB | 7 | 0.629 | 716.8 | 469,762,048 | 3 |
| gutmann @ 64 MB | 35 | 5.694 | 394.9 | 2,348,810,240 | 3 |
| zero1 @ 256 MB | 1 | 0.464 | 565.1 | 268,435,456 | 3 |
| dod3 @ 256 MB | 3 | 1.617 | 481.8 | 805,306,368 | 3 |
| dod7 @ 256 MB | 7 | 3.706 | 483.9 | 1,879,048,192 | 3 |
| gutmann @ 256 MB | 35 | 26.142 | 343.0 | 9,395,240,960 | 3 |

Throughput sits in a 480–720 MB/s band for every standard except the large
Gutmann runs, where it falls off to 343 MB/s. That fall-off is the one place the
shape of the cost changes, and it has an obvious cause: `gutmann @ 256 MB`
writes 9.4 GB, where every other row writes under 2 GB. A sustained nine-
gigabyte write stops being a memory-speed operation and becomes a device-speed
one.

**The bytes written scale with the pass count and nothing else.** Gutmann writes
35× the target's size, dod7 writes 7×, dod3 writes 3×. Choosing a standard is
therefore choosing a multiplier on the erase time, and the multiplier is exactly
the number of passes.

Extrapolating these rates to a 1 TB drive — which assumes a device that sustains
them, and no real device does for hours on end — gives the practical shape of
the decision:

| standard | passes | bytes written for 1 TB | time at the measured rate |
|---|---|---|---|
| `zero1` | 1 | 1 TB | ~31 minutes |
| `dod3` | 3 | 3 TB | ~1.8 hours |
| `dod7` | 7 | 7 TB | ~4.2 hours |
| `gutmann` | 35 | 35 TB | ~29.7 hours |

This is the reason the tool states the cost before an operator commits. The
confirmation card reports the bytes to be written and the pass count — `size ×
passes`, which is exact rather than estimated — next to the token that has to be
typed to proceed. On a 1 TB drive under Gutmann it reads:

> Will write 31.83 TB over 35 passes across 931.32 GB of media (35x the target).

No duration is shown there, deliberately. A time estimate would have to assume a
sustained rate on a device the tool has not measured, and a confidently wrong
"about 40 minutes" in front of the nineteen-hour operation in the table above is
worse than no estimate. The measured rates in this section exist to inform the
choice; the UI confines itself to the figure it can state as fact.

### 7.2 Verification cost

| subject | median_s | overhead vs unverified | min | max | bytes read back | repeats |
|---|---|---|---|---|---|---|
| none @ 256 MB | 0.663 | 1.00 | 0.365 | 2.723 | 0 | 7 |
| sample @ 256 MB | 0.675 | **1.02** | 0.408 | 0.886 | 67,108,864 | 7 |
| full @ 256 MB | 0.762 | **1.15** | 0.484 | 0.802 | 268,435,456 | 7 |

**FULL verification costs 15% over an unverified write, while reading back four
hundred times as much data as doing nothing.** The reason is that the write is
the expensive part: verification is a read, and a read of just-written data is
served at memory speed. An operator who declines full read-back to save time is
saving a seventh of the operation and giving up the ability to say the media was
checked.

**SAMPLE is within 2% of no verification at all**, which is the point of
sampling: it reads 64 of 256 MiB in evenly-spread windows and buys a
proportionate amount of assurance. It is not a substitute for FULL — it can miss
a localized failure between windows, and the report says so — but it is
effectively free.

#### How this measurement was got wrong twice, and what fixed it

This section is retained in full because the failure mode is more instructive
than the number.

The harness first reported SAMPLE at 1.64× and FULL at 1.29× — reading a quarter
of the media as dearer than reading all of it. That looked like noise, so a
seven-sample floor was added. It then reported SAMPLE at **0.54×** and FULL at
**0.74×**: a *saving* from doing strictly more IO. Interleaving the modes in
rounds was not enough either; the same run shape still produced 0.41×.

`tools/probe_verify.py` was written to run four candidate designs side by side
and print every sample, and the cause turned out to be the target, not the
harness. A long-lived scratch file that has already been filled with the pattern
being written is **not the same target on the second write**: the later samples
write the same bytes over the same bytes, out of page cache, and come out
cheaper. Whichever mode ran first absorbed that cost, so the ratio between the
modes was really a ratio between their positions in the sequence.

The design is now one freshly created target per sample, in a seeded random
order, and it produces the monotone 1.00 / 1.02 / 1.15 above. It is pinned by a
test (`test_the_verification_benchmark_erases_clean_media_every_sample`) rather
than left to survive on its merits.

#### Reading these numbers on other hardware

**The ratio is the portable figure; the absolute times are not.** The machine
behind this document is shared, and the `none` median alone was measured at
0.539 s and at 0.898 s in two different invocations of the probe — a 1.7×
swing on identical work. `seconds_min` and `seconds_max` are therefore published
alongside every median, and the `none` row's own spread (0.365–2.723) is wider
than the entire difference between the three modes. Anyone quoting 1.15× should
quote the spread with it.

`bytes_read_back` is taken from the engine's own accounting rather than
recomputed from the mode, so the ratio can be checked against the work actually
done.

### 7.3 Carving throughput and recovery accuracy

| subject | median_s | MB/s | artefacts | high-conf | planted | recall | precision | peak alloc |
|---|---|---|---|---|---|---|---|---|
| deleted_files.img (16.00 MB) | 0.603 | 26.5 | 11 | 9 | 10 | **0.90** | **1.00** | 16.04 MB |

Recall and precision are the two figures in this document measured against
cryptographic ground truth: every planted file in the synthetic FAT16 image has
a recorded SHA-256, and a recovered artefact counts only if its digest matches.

**Precision 1.00 means the scan produced no false positives at all** — every
artefact it reported was a real file that had been planted. **Recall 0.90 means
it found 9 of the 10 deleted files.** The one it missed is the plain-text
fixture, which has no magic number: prose has no signature, and the tool says so
rather than guessing. That is a deliberate limit of signature-based carving, and
it is recorded in §9 of the validation document rather than hidden in a recall
figure.

26.5 MB/s is the scan rate with the native backend active, on warm cache. Note
that this is *lower* than the 33.5 MB/s the pure-Python path reached on the
earlier run, and the difference is measurement noise on a shared machine rather
than a regression: the two configurations differ in which optional library is
importable, not in the scan loop, which is the same code either way. The figure
to trust across runs is the peak allocation, which did not move.

### 7.4 Carve scaling — the memory claim

| subject | seconds | MB/s | peak Python allocation |
|---|---|---|---|
| zero-filled image @ 32 MB | 1.189 | 26.9 | 16.01 MB |
| zero-filled image @ 128 MB | 4.010 | 31.9 | **16.01 MB** |

An image **four times larger** allocates the **same** 16.01 MB, and throughput
is flat across the two sizes. This is the check §4 describes: if the carver were
buffering the source, peak allocation would have grown towards 128 MB. It does
not, so a 2 TB device can be scanned in the memory a 32 MB image needs. The
16 MB floor is the chunk buffer, not a function of the input.

### 7.5 File and folder erasure

| subject | median_s | files/s | MB/s | repeats |
|---|---|---|---|---|
| 100 files @ 25 KiB | 4.530 | 22.1 | 0.5 | 3 |
| 1000 files @ 25 KiB | 48.198 | 20.7 | 0.5 | 3 |

Ten times the files takes 10.6 times as long, so the cost is dominated by the
per-file work — a `dod3` overwrite plus metadata cleansing on each — and the
rate holds at roughly 21–22 files per second. Throughput in MB/s is low and
should be ignored here: 25 KiB files cannot amortize per-file overhead, and the
figure is reported only so that a reader comparing it against §7.1 does not
mistake one for the other. The number that matters for planning is **files per
second**, because that is what a bulk deletion of 50,000 documents costs.
